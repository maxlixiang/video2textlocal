## 实际异常与修复

第一次独立测试协调器复用媒体时遇到只读挂载，只有验收文件的 coordinator 覆盖层开放自己的媒体卷写入，用于复制三个明确文件。**生产 manager 媒体挂载保持只读**；不是产品依赖的文件写入方式，也没有再次请求抖音。

首次实际 DeepSeek 整理触发 `polish_truncated`，只发送了完整原稿，没有把截断内容伪装为完整整理稿。按 [DeepSeek 官方思考模式接口](https://api-docs.deepseek.com/guides/thinking_mode/) 增加配置 `DEEPSEEK_THINKING`，默认显式 disabled；思考设置纳入缓存键，失败块记录 finish_reason/usage 而不提交结果。保持用户 `.env` 中的 `deepseek-flash` 模型，未改密钥或提高费用预算。重试同一任务后成功，只有新整理稿补发。

首次截断记录仅包含程序错误码，没有原始响应 token usage，因此不能据此精确断言当时消耗了多少推理 token；显式关闭思考后的实际调用完成是修复可行性证据。

本轮主机受限执行环境的 asyncio 跨线程唤醒测试挂起；无网络独立容器中完成回归，挂起的明确本轮进程已终止。没有安装宿主依赖或修改安全/网络设置。

## 限制与未验证

真实选择消息由 Telegram 发送；验收回调在本地分派，**未声称用户真实点击或长轮询收到更新已验证**。28 项离线测试包含三个回调去重和归属判断。

YouTube/X 新的视频模式与标题解析已实现，尚未重新进行三平台整组在线下载发送；本轮只使用抖音样本。X 标题查询为可选第三方依赖；无标题旧缓存使用平台和作品 ID。

[Telegram 官方新上传限制](https://core.telegram.org/bots/api#sending-files)为 50 MB；超限文件保留并明确提示，不能通过重试解决。未引入本地 Bot API、自动压缩/分片或公开文件服务。

DeepSeek 忠实度需人工核对，尤其原稿本身的识别错误与名称；未宣称自动修正事实或逐字准确。本轮 Windows 子进程预算仍为 2 GiB，没有擅自修改先前讨论的内存策略。
